# Регулярное обновление публичного HTML

`npm run refresh:prerender` выполняет полный цикл: проверка типов → анонимная
сборка по публичному API → проверка всех HTML в Chromium с отключённым JavaScript →
замена `dist-prerender`. В отличие от `build:prerender`, проверка готовых HTML здесь
обязательна **до** замены предыдущего результата.

## Локально

Задайте `PRERENDER_SITE_URL` настоящим HTTPS origin будущего сайта и
`PRERENDER_API_URL` адресом доступного сборщику API (локально `http://127.0.0.1:8000`).
Команда не угадывает публичный домен. Точные ограничения переменных и установка
Chromium описаны в [README](../README.md#публичный-html-поиск-и-превью-ссылок).

```powershell
npm run refresh:prerender
npm run refresh:prerender -- --watch
```

Первый вариант однократный и подходит для ручного обновления после публикации.
Второй выполняет цикл сразу, затем через пять минут **после завершения** предыдущего.
Интервал задаётся `PRERENDER_REFRESH_INTERVAL_MS` (15000–86400000 мс).
Неудачный цикл оставляет предыдущий HTML и повторяется после того же интервала;
однократный запуск завершается с ненулевым кодом. Остановка Ctrl+C/SIGTERM дожидается
завершения текущего цикла. Обычный Vite dev уже получает свежие данные из API и не
нуждается в таком процессе; цикл нужен для статических HTML и превью ссылок.
Служебная `.data` и готовый `dist-prerender` исключены из Vite watcher, чтобы
локальный dev-сервер не наблюдал за перемещаемыми каталогами артефактов.

## Блокировка, состояние и восстановление

- `.data/prerender-refresh.lock` исключает параллельные запуски **этой команды**.
  Дополнительный запуск пишет `Skipped` и завершается успешно. Не запускайте
  одновременно старую `build:prerender`, которая предназначена для ручной сборки.
- `.data/prerender-refresh/status.json` содержит состояние последней попытки,
  время начала/окончания, `last_success`, число страниц или сообщение об ошибке.
  Файл заменяется целиком. Подключите его к мониторингу на своём сервере; старый
  `last_success` при работающем процессе также требует внимания.
- `.data/prerender-refresh/previous` сохраняет предыдущий полный артефакт.
  Временный кандидат удаляется при обычной ошибке, рабочая БД не используется для
  записи. Все API-запросы остаются анонимными GET из существующего allowlist.
- Переименование каталогов при `EPERM`/`EBUSY` выполняется не более чем в семь попыток
  с задержками 100, 250, 500, 1000, 2000 и 4000 мс (суммарное ожидание 7,85 с).
  Та же защита действует при откате и восстановлении прерванной публикации.
  Постоянный отказ завершает команду с ошибкой и точными путями в журнале/статусе;
  `error_code` сохраняет системный код. Если заблокирован и откат, сообщение явно
  указывает, где сохранён предыдущий полный артефакт. Устраните держатель файлов
  перед повтором; скрипт не завершает посторонние процессы. Конкретный держатель
  Windows-блокировки по одному коду `EPERM` не определяется.
- После аварийного завершения процесса lock сохраняется намеренно: автоматический
  захват по таймауту мог бы запустить второй сборщик при долгом первом цикле.
  Прочитайте PID из lock, убедитесь в диспетчере задач/`ps`, что сборщик завершён,
  затем удалите **только** `.data/prerender-refresh.lock` и повторите команду.
  После обрыва между переименованиями каталогов предыдущий HTML восстанавливается
  перед новой сборкой. Осиротевшие `candidate-*` внутри этого каталога можно удалить
  после остановки сборщика; они не публикуются.

## На сервере

Примеры [systemd service](beavers-prerender.service.example) и
[timer](beavers-prerender.timer.example) запускают ту же однократную команду каждые
пять минут. Скопируйте их без `.example`, укажите пользователя, путь checkout,
путь Node и отдельный EnvironmentFile с реальными origin. Сначала установите
зависимости через `npm ci` и Chromium от имени пользователя сборщика. Затем
проверьте однократный запуск и только после этого включайте timer. Сервис должен
иметь доступ к API и запись в checkout; административные токены ему не нужны.
Не включайте одновременно timer и `--watch`.

Скрипт обновляет локальный артефакт, **не выполняет удалённый деплой**.
Он использует два переименования каталогов с откатом при ошибке; между ними
существует короткий промежуток, поэтому для сайта без перерыва не обслуживайте
перезаписываемый build-каталог напрямую. На Linux копируйте полностью готовый
`dist-prerender` в новый каталог release, затем атомарно заменяйте симлинк `current`,
который указан в Nginx `root`. Храните предыдущий release для отката и запускайте
копирование/переключение в том же одиночном задании после успешного refresh.
Конкретный deploy зависит от выбранного хостинга и пока не включён.

При публикации, скрытии или удалении материала можно дополнительно запускать
этот же service/deployment job вручную. Периодический запуск остаётся страховкой:
изменение данных появится в HTML после следующего успешного цикла. Live API и Vue
обновляют данные независимо от снимка.
