# Workflow разработки для Codex

В этой ветке находится переносимый пакет [codex-workflow](../codex-workflow/README.md), используемый для последовательной разработки с проверками и независимым ревью. Это инструмент работы Codex над проектом. Он не является workflow редакционного агента Бобрика, GitHub Actions или частью публичного сайта.

## Этапы

```text
grill-with-docs → to-spec → to-tickets → implement → code-review → complete
```

| Этап | Результат |
|---|---|
| `grill-with-docs` | Требования, факты из кода и первичных документов, противоречия и открытые решения |
| `to-spec` | Ограниченная спецификация с поведением, исключениями и проверяемой приёмкой |
| `to-tickets` | Локальные задачи, зависимости, области владения файлами и проверки |
| `implement` | Изменения в заявленных областях и выполненные проверки текущего кода |
| `code-review` | Независимое ревью того же снимка исходников и результатов |
| `complete` | Завершение только после актуальных финальных проверок и ревью |

Замечания возвращают работу к затронутому этапу. Переход между этапами сам по себе не требует нового разрешения пользователя. Запрос остановиться после конкретного этапа сохраняет силу.

## Что входит

- Шесть навыков: координатор и пять этапов.
- Шесть ролей: lead, researcher, architect, implementer, reviewer, QA.
- Python runtime с состоянием, графом задач, ownership, блокировками проверок и снимками исходников.
- Установщик с dry-run, учётом принадлежащих пакету файлов, обновлением и удалением.
- Проверка обнаружения навыков без модельного запроса и тесты пакета.
- [Контрольные суммы исходных файлов](../codex-workflow/PACKAGE-MANIFEST.json) и [отчёт текущей проверки](../codex-workflow/VERIFICATION.md).

Роли наследуют модель и provider. Пакет не содержит ключей, глобального `config.toml`, пользовательских сессий и прошлых task ledgers. Runtime сам не запускает модели: реальное делегирование и оценку достаточности доказательств выполняет Codex.

## Установка на другой машине

Нужен Python 3.11+ и установленный Codex. Из корня репозитория сначала проверьте план установки:

```powershell
python codex-workflow/install.py --dry-run
```

Затем установите пакет:

```powershell
python codex-workflow/install.py
```

Установщик по умолчанию использует `$CODEX_HOME` или `~/.codex`; не меняет существующий глобальный `config.toml`, provider или посторонние роли. Неизвестные конфликты имён останавливают запись. Для изолированной проверки используйте `--target <отдельный-каталог>`.

Это пакет текущей локальной схемы навыков/ролей; совместимость обнаружения с другой версией Codex проверяется отдельно. Для fresh registry probe:

```powershell
python codex-workflow/verify_install.py --workspace .
```

Эта проверка не выполняет inference и не доказывает реальный запуск каждой роли. После установки начните новый чат Codex. Если специализированные роли не рекламируются средой, координатор использует доступные роли с теми же инструкциями, не выдумывая запуск агента.

## Использование

Для новой задачи:

```text
$agent-workflow Реализуй <задачу> в этом проекте. Сохрани несвязанные изменения и пройди актуальные проверки и независимое ревью.
```

Для продолжения:

```text
$agent-workflow Продолжи запуск из <путь к каталогу запуска>.
```

Выбирается достаточный режим `light`, `standard` или `full`; число агентов определяется работой. Запуски и доказательства хранятся в игнорируемом каталоге либо вне source tree. В этом frontend уже игнорируется `artifacts/`: пример каталога — `artifacts/agent-workflow/<task-id>`.

План Бобрика и питомец находятся в [отдельной ветке](https://github.com/Dembler/predatory-beavers-website-new-frontend/tree/codex/bobrik-plan-and-mascot-20261116/docs/bobrik). Эта ветка workflow основана на main и не объединяет реализацию или материалы другой ветки автоматически. Перед работой над Бобриком используйте согласованный план как источник требований в выбранной рабочей ветке.

Одобрение задачи не означает автоматический push, merge, deploy или отправку сообщений. Эти действия требуют соответствующего пользовательского поручения. Настоящая передача пакета в GitHub не запускает реализацию сайта.

## Локальные проверки пакета

```powershell
python -m pytest codex-workflow/tests -q -p no:cacheprovider
```

Для тестов требуется pytest; сам runtime и установщик используют стандартную библиотеку Python. Тесты работают с временными каталогами. Повторная проверка на другой машине должна учитывать доступные права symlink и установленную версию Codex. Успешные тесты инструмента не заменяют проверки приложения, браузера и production.
